# research-pod-split.md — один бинарь на несколько подов: решения, проверки, открытые пункты

> Статус: **схема перенесена** в шаблон `full` и SDK (раздел «Splitting one binary across pods» в `README.md`).
> Здесь — то, что в коде не видно: почему сделано так, что подтвердил живой стенд, на какие грабли наступили и что
> осталось открытым. Дата: 2026-10-02. Источник — эксперимент на боевом сервисе (REST API + тик-воркеры +
> AMQP-консьюмеры + transactional outbox), проверенный в kind и на compose-стенде полным функциональным набором.

## 0. Коротко

- Процесс собирается **из опций**, которые команда перечисляет руками: `WithServer(addr, наборы…)`, `WithWorkers()`,
  `WithConsumers()`. Типа ролей, env-переключателя ролей и автоматической раскладки listener'ов нет — что процесс
  запускает и где слушает, читается из команды.
- Один вид сервера. «Debug-сервер» — это `WithServer` с техническими наборами. Middleware-цепочка запросов принадлежит
  набору `Install`, а не серверу, поэтому набор ведёт себя одинаково на любом порту.
- `serve` = всё в одном процессе (поведение single-pod не меняется), `http` / `worker` / `consumer` — подмножества.
  Разнести деплой — правка values: тот же образ, другая команда.
- На стенде (2 `http` + `worker` + `consumer`) весь функциональный набор зелёный. Нашлись три проблемы не самой схемы,
  а запуска и выкатки: гонка миграций, потеря запросов при выкатке `http`, старт воркеров раньше схемы (§4).
- В skit открытыми остаются семь пунктов (§7; три закрыты 2026-10-02). Самые весомые: миграции без session-lock, нет
  паузы перед закрытием listener'а, процесс с одним только API дозванивается до брокера.

## 1. Задача

Один бинарь должен разворачиваться и как один под (`serve`), и как несколько: HTTP отдельно и на N реплик, тик-воркеры
отдельно и ровно одной репликой (там wall-clock cron и синглтоны), консьюмеры отдельно (competing consumers, реплик
может быть несколько). Изначальный вариант — тип `Roles`, который протаскивался через сервер, контейнер и хендлеры
и включал куски условиями `if roles.Worker {…}`. Требование: тип ролей убрать целиком, состав писать явно рядом с запуском.

## 2. Решения и почему

| # | Решение | Почему |
|---|---|---|
| 1 | Состав процесса = список опций в команде | Добавить, убрать или объединить команду — правка списка. В пакете сервера нет ни одного `if` про роль или раскладку |
| 2 | Роль выбирается **командой**, не env | Секрет-`.env`, общий для всех релизов приложения, приезжает во все поды. Если загрузчик env делает Overload (`godotenv.Overload`), значение из файла ещё и перебивает env пода. Аргумент команды не перебивается ничем |
| 3 | Технические роуты — наборы `Health`, `Metrics`, `Pprof`, `Info` (`Debug` = все), монтируются на любой `WithServer` | Где их отдавать, решает команда: рядом с API или на своём порту — правка одной строки, а не опция с ветвлением в сборке. Прежняя env-опция «адрес debug-сервера», раскладывавшая listener'ы автоматически, отвергнута: «разработчик сам решает, где подключать» |
| 4 | Цепочка запросов (trace, access log, метрики, timeout, лимит тела) — у `Install` | На общем порту технические роуты шли через бизнес-цепочку: каждый scrape `/metrics` и проба попадали в access log и счётчик запросов, pprof-профиль резался request timeout'ом, трейсингу нужен был ручной список исключённых путей. Теперь технический набор ведёт себя одинаково на любом сервере |
| 5 | Сборка и запуск разделены: `New` строит и монтирует, `Run` только запускает | Процесс без опций — только контейнер (one-shot команды). Ничего не строится «на всякий случай» |
| 6 | Кильсвитчи отдельных воркеров не трогали | Это конфигурация, а не композиция: команда решает, есть ли `WithWorkers()`, кильсвитч — какие из воркеров стартуют |
| 7 | Наблюдаемость: `GET /debug/components` + строка `starting` в логе с теми же полями | Счётчики читаются из приложения в момент запроса, поэтому учитывают и кильсвитчи. По ответу видно, что реально крутится в поде |
| 8 | Recover паник — один, в корне роутера сервера (`r.Use(middleware.Panics(log))` в `a.handler`); внутри цепочки `Install` 500 от паники пишет access log (`RecoverPanics`) | Пересмотрено: per-route recover в `router.Handle` тянул логгер в `router.New`, прятал `routegroup.Bundle` (а с ним `NotFoundHandler`, `HandleFiles`) и связывал `middleware` с httplog. Корень ловит панику технических наборов и всё, что вышло из цепочки `Install` |
| 9 | Тип кирпича называется `Option` (функциональные опции `With…`) | Выбор пользователя; варианты `Component` / `Brick` отвергнуты |

Сознательно иначе, чем в исходном сервисе: в skit технические роуты по умолчанию на своём `DEBUG_ADDR` (pprof не на
публичном порту); у `worker`/`consumer` нет своих адресов-флагов, потому что skit грузит `.env` через `godotenv.Load`
(не Overload) и порт локально сдвигается `DEBUG_ADDR=… go run . worker`; пустой адрес в `WithServer` — сервера нет.

## 4. Что показал живой стенд

Стенд: kind, 3 ноды, 2 реплики `http` (`migrate up && http`), 1 `worker`, 1 `consumer`, все Deployment применены разом
(как это делает GitOps-синк). Инфраструктура — docker-compose, ноды kind подключены к его сети. Функциональный набор
(~80 файлов HTTP-сценариев) гонялся без правок: Service на NodePort проброшен на тот же `localhost:8080`, что и у
compose-приложения.

Подтвердилось:

- Набор зелёный на `serve` (compose), на сплите в compose и в kind. Кильсвитч воркера проверяется сменой env у всех
  подов (ConfigMap + `rollout restart`): у worker-пода счётчик воркеров в `/debug/components` падает на один.
- `/debug/components` по подам совпадает со строкой `starting`; бизнес-роут на worker/consumer — 404, на http — 401
  (авторизация сработала, роут смонтирован); `/health` — 200 у всех.
- `kubectl delete pod` у worker/consumer — штатное завершение за миллисекунды, новый под готов через ~3 с.
- PID 1 в поде — сам процесс: `sh -c "a && b"` (busybox) exec'ает последнюю команду, так что SIGTERM доходит без явного `exec`.
- Холодный старт на пустой БД до готовности всех подов — ~80 с.

Нашлось (к самой схеме не относится, но вылезает именно при разнесении):

1. **Гонка миграций.** Две реплики API накатывали миграции одновременно: часть миграций применилась дважды (дубли
   в таблице версий; обошлось, потому что миграции были идемпотентны — `IF NOT EXISTS`, `ON CONFLICT DO NOTHING`),
   у второй реплики одна упала. Хуже того, команда `migrate up` в том сервисе всегда завершалась с кодом 0, и упавшая
   реплика всё равно стартовала (`migrate up && http`). В skit `migrate` ошибку возвращает, но lock'а тоже нет — §7.1.
2. **Выкатка `http` теряет запросы.** `rollout restart` под непрерывным потоком: без `preStop` — 3–12 ошибок
   (`Connection reset by peer`) за выкатку, ровно в первые ~150 мс после перехода старого пода в Terminating: процесс по
   SIGTERM сразу закрывает listener, а Service ещё шлёт на него трафик. С `preStop: sleep 5` — 0 ошибок в 4 выкатках
   из 5 (в одной 6). §7.2.
3. **Воркеры стартуют раньше схемы.** Первые тики worker-пода — `relation … does not exist`, со следующего тика
   проходят сами, рестартов нет. Ожидаемо, пока миграции катит релиз с API; если без новой схемы код не работает —
   sync waves или миграция отдельным Job.
4. **Процесс с одним API всё равно ходил в брокер** — outbox-модуль при сборке контейнера принудительно создавал
   confirm-mode publisher, поэтому `http` не стартовал без RabbitMQ. В шаблоне skit то же самое — §7.3.

## 5. Грабли

- **Загрузка `.env` с Overload** перебивает env пода значением из примонтированного файла. Всё, что должно различаться
  между подами (состав, порты), — только командой и её флагами. В skit `.env` грузится без Overload, но секрет-файл
  общий у всех релизов приложения, так что правило то же.
- **`kubectl apply` не откатывает ручной `kubectl patch`** (strategic merge + last-applied): env, добавленный патчем,
  остаётся. Убирать явно: `kubectl patch --type=json -p '[{"op":"remove","path":"/spec/template/spec/containers/0/env"}]'`.
- **GitOps синхронизирует все релизы приложения разом** — новый worker может подняться до миграций (§4 п. 3).
- **Тестовый харнесс без контейнера.** Тест опций собирает приложение без инициализации контейнера, если какой-то
  инициализатор при сборке ходит в БД (в skit-x так было с audit log): иначе юнит-тест требует Postgres.
- **Счётчик воркеров зависит от кильсвитчей**, поэтому ожидаемые значения в проверках `/debug/components` брать из
  конфигурации стенда, а не хардкодить.

## 6. Деплой: три релиза одного чарта

Проверено на конфигурации (helmfile + общий чарт), в прод не выкатывалось — уроки общие:

- **Команда пода — `args`** (заменяют `CMD` образа; `ENTRYPOINT` в образе нет). Цепочка — через шелл:
  `["sh", "-c", "app migrate up && app http"]`; одиночная — без: `["app", "worker"]`. `CMD` образа не менять: это
  команда по умолчанию для всех, кто его запускает.
- **Базовый values + маленький файл отличий** на релиз; тег образа — только в базовом.
- **API-релиз переводится на `http` в том же коммите**, что добавляет worker. Иначе воркеры работают в двух подах
  (старый `serve` + новый `worker`), и cron срабатывает дважды.
- **worker**: `replicaCount: 1`, `rollingUpdate: {maxSurge: 0, maxUnavailable: 1}` — старый под гасится до старта
  нового, иначе при выкатке два воркера поработают одновременно; без `migrate`; без ingress (именно `null` — `{}` при
  слиянии values ingress не удалит); PDB выключить (`minAvailable` в процентах при одной реплике блокирует drain ноды);
  аннотация reloader'а — на секрет своего релиза.
- **consumer**: обычный rolling update подходит (competing consumers), без ingress.
- **Пробы и Service не меняются**: каждая команда держит сервер с `Health`, поэтому одна конфигурация проб на все поды.
- **Миграции** — только в API-релизе, а лучше один раз до старта реплик (Job / sync wave / session-lock, §7.1).
- **Проверка перед мержем**: `helmfile template` — три Deployment, ingress только у API, у каждого свои `args`.
  После выкатки — `/debug/components` по подам.

## 7. Открытые пункты в skit

1. **Миграции без session-lock.** `migrate.New` строит `goose.NewProvider(dialect, db, fsys)` без
   `goose.WithSessionLocker(...)`. Реплики, которые катят `migrate up` при старте, гоняются (§4 п. 1). В goose v3.27
   есть `lock.NewPostgresSessionLocker()` — передавать по умолчанию для Postgres (опцией `migrate.New` или всегда).
2. **Нет паузы перед закрытием listener'а.** `httpserver.Stop` → `Shutdown` сразу закрывает listener, а Service ещё
   шлёт трафик (§4 п. 2). Варианты: задокументировать `preStop: sleep N` в шаблоне деплоя; или на SIGTERM сначала
   переводить `/readyz` в 503 и ждать настраиваемую паузу (`SHUTDOWN_DELAY`), потом `Shutdown`.
3. **Процесс без воркеров дозванивается до брокера.** `deps/broker.go.tmpl` при `Broker.Enabled` сразу делает
   `rabbitmq.Dial` + `NewPublisher` в каждом процессе, включая реплики `http`; outbox-хранилище (нужна только БД)
   привязано к тому же флагу. Разделить: `Outbox` (store, только БД) — всем, кто пишет события; `Publisher` + relay —
   лениво, только из `WithWorkers`; соединение консьюмеров — только из `WithConsumers`. Итог: `http` не открывает AMQP.
4. ~~**У HTTP-запросов нет серверного спана.**~~ Сделано 2026-10-02. Откуда взялось: эталонная схема открывала span
   на запрос в самом web-слое (при обработке хендлера — span + `traceparent` в ответ); в `rest/router` перенесли только
   `InjectTracing` (tracer и trace id в контексте), а открытие спана и `traceparent` потерялись, otelhttp не было никогда.
   Без спана `rest/mid.Errors` писал `RecordError` в удалённого родителя или noop, а исключения сэмплера по маршрутам ни
   на что не действовали. Теперь первым в цепочке `Install` шаблона стоит `otelhttp.NewMiddleware` (span назван по
   маршруту — `r.Pattern`, `GET /hello`); провайдер — глобальный, его ставит `otel.InitTracing`. `middleware.TraceRequest`
   больше не извлекает заголовки поверх уже открытого спана (иначе подменял бы серверный span спаном вызывающего — это
   и ловит `TestTraceRequestKeepsServerSpan`) и span не закрывает: урок исходного сервиса — там `defer span.End()`
   закрывал otelhttp'шный span до записи ответа, и терялись статус Error и `http.response.status_code`. Тест шаблона
   `TestInstallTracesRequests`: один server-span на `/hello` с кодом ответа, ни одного — на технических наборах.
5. ~~**`otel.AddSpan` без tracer в контексте возвращал родительский span**~~ — сделано 2026-10-02: `AddSpan` и `AddSpanAt`
   возвращают `noop.Span{}`; тесты `TestAddSpanNoTracerLeavesParentOpen`, `TestAddSpanAtNoTracerIsNotParent`.
6. **404/405 под префиксом API проходят мимо цепочки `Install`** (нет ни access log, ни метрик, ни трейса): цепочка
   висит на маршрутах группы, а неизвестный путь или метод mux отвечает сам. Ошибку вызывающего (переименовали ручку,
   шлют не тот метод) видно только в логах ingress. Варианты: catch-all в группе (но 405 превратится в 404);
   `NotFoundHandler` на корне, обёрнутый в цепочку (только 404); лог и счётчик на корне сервера.
7. ~~**`traceparent` в ответе бизнес-ручек**~~ — сделано 2026-10-02: `otel.InjectToResponse` пишет W3C `traceparent` /
   `tracestate` серверного спана (только своего: удалённого родителя не эхоит, baggage не пишет), вызывается из
   `middleware.TraceRequest` до хендлера. Без серверного спана заголовка нет — это осознанно.
8. **Readiness проверяет только Postgres.** Consumer-под, у которого упали консьюмеры или нет брокера, остаётся Ready и
   не перезапускается. Покомпонентные проверки: брокер — там, где есть `WithConsumers`. Liveness уже process-only
   (`health.Liveness()`), это правильно: блип БД не должен перезапускать поды.
9. **Мелкие опции, когда понадобятся.** `WithWorkers` смешивает безопасные для N реплик воркеры (outbox relay —
   lease + `SKIP LOCKED`) и синглтоны (cron). Можно разбить на `WithOutbox` / `WithJobs`, оставив `WithWorkers` = все;
   команды не меняются, а доставку можно масштабировать отдельно от cron. Синглтон-cron в N репликах — через
   `lock.Locker` (`skit add cron --lock postgres`).

10. **Sampler: `ParentBased` и исключения по имени спана** (`otel/sampler.go`). Исходный сервис от обоих отказался:
    `ParentBased` переносит долю сэмплирования к вызывающему — upstream, сэмплирующий на 100%, затягивает спаны сервиса
    на 100% в обход его собственной probability; исключения по имени спана нужны, только если серверный спан стоит на
    всём mux, а с цепочкой на `Install` технические роуты спанов не порождают (`ExcludedRoutes` шаблона — `GET /healthz`,
    `GET /readyz` — теперь страховка на случай, если otelhttp поставят на весь сервер). Остаётся решить про
    `ParentBased`.

Идея, не план: декораторы для бизнес-спанов — обёртка над интерфейсом домена, включаемая при сборке, вместо
`AddSpan` внутри методов core. Ложится на сборку из опций, но это обёртка на каждый интерфейс.

## 8. Что сознательно не взято

- **Тип ролей / профилей** и env-переключатель состава — см. §2 п. 1–2.
- **otelhttp вокруг всего mux + фильтр по путям.** Нужен список исключений для технических ручек, а фильтр по
  `url.path` зависит от имени атрибута semconv. С цепочкой на `Install` исключения не нужны. Пересмотреть, если на
  корне появится middleware, которая отвечает сама (rate limit, auth), и её отказы нужно видеть в трейсах.
- **Отдельный span на отправку ответа** — дублирует то, что пишет серверный span.
- **Тест «секреты не отдаются по HTTP»** — шаблон не отдаёт конфиг. Если появится `/debug/config`, взять приём:
  тест рефлексией обходит структуру конфига и требует `json:"-"` у полей с `Password`/`Secret`/`Credentials`/`DSN` в имени.
- **Проверки, которые в skit уже выполнены** и в исходном сервисе были багами: `Content-Type` до `WriteHeader`
  (`rest`, `health`, `auth`, `debugsrv` — везде правильно), readiness → 503, trace_id в логах, OTLP-экспортёр,
  имя tracer'а.

## 9. Как повторить проверку

1. Один образ, kind-кластер (1 control-plane + 2 worker), NodePort Service проброшен на порт, который ждёт
   функциональный набор; инфраструктура — из compose, ноды подключены к его docker-сети.
